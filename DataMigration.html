Macquires CRM for Syriatel

Scope of Services — Data Migration Methodology & Tooling (RFP Section 3)

Data Migration Methodology & Tooling

Macquires will migrate Syriatel’s existing subscriber population into the new CRM using a defined Extract → Transform → Load (ETL) methodology. Migration is treated as a telecom delivery workstream—not an afterthought—so that showroom and back-office users inherit accurate customers, lines, SIM inventory, and package assignments before go-live.

Macquires will provide the database strategy for the target CRM schema, the tooling to execute bulk loads with row-level accountability, and a readiness checklist of what Syriatel must supply before each wave runs. Loads are rehearsed in a staging environment; production cutover proceeds only after agreed reconciliation and error-rate thresholds are met.

Migration tools & database strategy

RFP requirement — specify tools, scripts, and ETL frameworks

Macquires will deploy a combination of schema-deployment tooling on Microsoft SQL Server and an embedded CSV bulk-import ETL framework that is already part of the Syriatel CRM build. Legacy BSS/OSS data is extracted by Syriatel (or jointly scripted), transformed to Macquires-approved templates, and loaded into the CRM subscriber data model through audited background jobs supervised from the Bulk Import Monitor.

Macquires does not propose a separate proprietary warehouse for subscriber migration. The production CRM database is the system of record once a wave is signed off; optional staging databases use the same schema for dress rehearsal only.

Database strategy

Macquires will prepare the target database in two steps: first structural readiness (tables, indexes, encryption for national ID), then phased data loads. Subscriber-related data lands in the telecom domain tables below—aligned to how the CRM runs activations, SIM operations, and package changes after cutover.

Schema deployment (before any data load)

Macquires will apply Entity Framework Core migrations with the application release, supplemented by idempotent manual SQL scripts documented in the telecom migration runbook (including enterprise bulk-import tables and subscriber-profile indexes). This ensures the CRM database structure is identical in staging and production before Syriatel files are uploaded.

Phased migration methodology

Macquires will execute migration in dependency order so reference data and inventories exist before subscriber bindings. Each phase ends with a formal gate: error export reviewed, reconciliation signed by Syriatel, then authorization for the next wave.

  1. Schema and environment — Staging and production CRM databases; bulk-import configuration and encryption keys.
  2. Telecom reference data — Customer groups/categories, subscription types, product catalog and offering codes (required for package migration).
  3. Wave A — Customers — CustomerProfiles bulk load; remediate row errors.
  4. Wave B — Numbers and SIMs — MsisdnAsset bulk load and/or ImportSimInventoryBatch for smaller deltas.
  5. Wave C — Subscriber binding — Link customer, profile, MSISDN, and subscription via API/scripts per signed mapping.
  6. Wave D — Packages — PackageMigration bulk load to align active lines to CRM offerings.
  7. Wave E — Cutover — Final delta, production load, joint sign-off.

Operational safeguards are built in: duplicate national IDs, customer codes, MSISDN, and ICCID are rejected with bilingual row errors; header mismatch fails the file before data rows run; jobs support up to 100,000 rows with batch commits and restart-safe queue processing.

Technical prerequisites

RFP requirement — formats, cleansing, and staging before execution

Macquires requires Syriatel to complete the prerequisites below before migration execution begins. These items are documented in a Data Migration Readiness Checklist issued at design phase; Macquires will not run production loads until mandatory rows are signed off by Syriatel’s data owner.

Database formats and extract deliverables

Syriatel must supply subscriber extracts in UTF-8 CSV matching Macquires templates exactly (header names are flexible for spacing/case; extra or missing columns cause rejection). Full production files are delivered per wave; anonymized samples of at least 1,000 rows per job type are required for staging rehearsal first.

Cleansing is performed before upload to Macquires loaders. The CRM enforces quality at load time; failing rows are recorded in InventoryBulkImportError and exported for correction—never silently skipped without audit.

Staging environments and infrastructure

Syriatel must provide a staging CRM environment (same schema as production) for full-volume rehearsal, plus the production target for cutover. Macquires will configure the bulk-import file area on the application server (or use authenticated HTTPS upload only). A service account with bulk-import permissions, VPN/private connectivity, field-encryption keys for national ID, agreed maintenance windows, and named BSS/DBA contacts for extract and count validation are mandatory.

At least one customer group and category must exist in CRM before customer load; catalog must be loaded before package migration. Privacy approval for transferring national ID and subscriber PII into CRM is required before any non-anonymized file is handled.

Migration gates and sign-off

Macquires will commence each production wave only when staging has met the agreed error-rate target (with documented waivers for known legacy exceptions), reconciliation counts are signed by Syriatel, the Bulk Import Monitor shows completed status, and sampled subscribers validate correctly in Customer 360. Each upload retains job ID, success/error totals, and auditable operator identity.

Scope clarity: The current CRM build includes the three bulk-import job types and APIs above. A single combined “full subscriber snapshot” file (customer + subscription in one row) is delivered in the migration program via Wave C binding and/or Macquires-authored extensions after mapping workshop—not as a separate product module. Historical billing ledger detail and CDR archives remain in legacy systems unless Syriatel scopes additional extract work.

Summary

Macquires will provide a SQL Server–aligned database strategy, an embedded CSV ETL framework with three approved load contracts, background processing and supervisor monitoring, phased waves with reconciliation, and optional joint extract scripting from legacy BSS. Syriatel will provide template-conformant cleansed extracts, mapping sign-off, telecom reference data, staging and production environments, security and privacy approvals, and formal sign-off between waves—before migration execution proceeds.
